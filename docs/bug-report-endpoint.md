# 报告投递端点配置

这份文档写给维护者：报告功能往哪儿投、配置在哪、换端点时改什么。
决策依据见 [ADR 0042](./adr/0042-bug-report-delivery.md) 决定 12 与 16；失败码与文案不在本文范围。

## 配置在哪

发布配置就是仓库里的 [`apps/desktop/resources/bug-report.json`](../apps/desktop/resources/bug-report.json)。
`electron-builder.yml` 的 `files: resources/**/*` 会把它打进 asar，所以**不需要**改打包配置。
主进程读配置时按两个候选路径找它（开发态是 `apps/desktop/resources/`，打包态在 asar 里），
读不到、JSON 坏、字段形状不对，一律按「未配置」处理并**不抛**——报告功能照样起来，只是少一个按钮。

```json
{
  "form": {
    "shareUrl": "https://<tenant>.feishu.cn/share/base/form/<shrcn…>",
    "fields": {
      "body": "报告内容",
      "meta": "版本与设备信息",
      "code": "错误代码",
      "file": "附件（选填）"
    }
  },
  "mailbox": "",
  "mailboxName": "",
  "subscribeUrl": "",
  "repository": ""
}
```

- `form`：飞书表单通道（默认收件端点）。`shareUrl` 与 `fields.body` 缺一个整段不生效。
- `mailbox` / `mailboxName` / `subscribeUrl` / `repository`：邮件与仓库通道，空串 = 未配置。
- 代发通道（`web3forms` / `formspree` / `eleckoi-relay`）只走环境变量，**文件里不配代发**。

## 列名与填写页标题

`report_body`（正文）、`report_meta`（版本/平台/签名）、`report_code`（失败码）、
`report_file`（附件）是飞书表里的**列名（字段名）**，保留用于管理和读取记录。

**客户端预填配置必须与填写页的题目标题一致。** 2026-11-06 在当前正式表单中实测：只把题目标题改成
中文、保留英文列名后，原英文预填参数失效；CLI 返回的字段 ID 也未预填。改用中文题目标题后恢复。
旧教程中「改题目标题不影响预填」的结论不适用于当前表单，不能继续据此改标题。

| 列名 | 填写页题目标题／客户端 `fields` 值 |
| --- | --- |
| `report_body` | 报告内容 |
| `report_meta` | 版本与设备信息 |
| `report_code` | 错误代码 |
| `report_file` | 附件（选填） |

参数名是 `prefill_<题目标题>`，共享构造器会编码中文。改题目标题时必须同步改 `bug-report.json` 的
`fields` 与 Android `strings.xml`，再验证实际预填及落表；已有发布版本使用旧标题时不能直接改掉。

## `/form/` 的坑

飞书 `+form-share-get` 返回的 `https://<tenant>.feishu.cn/share/base/<shrcn…>` 是 **Base 分享链接**，
未登录打开会 302 到登录页。能匿名填写的**表单填写页**是 `.../share/base/form/<shrcn…>`——
多一段 `form`。客户端不做推导也不校验形状（决定 12）：复制错就只是「表单打不开」，所以请从飞书界面
复制填写页地址，存完整链接。

当前正式收件端点为维护者团队的「ElecKoi 问题反馈」多维表格，填写页位于
`https://icnhqa31jmpu.feishu.cn/share/base/form/shrcnTVcCOAWeJGqYv7mBaWCgrg`。
桌面与 Android 已同步替换原测试 Base；维护者在飞书中打开多维表格查看收到的报告，
用户通过填写页提交，无需获得底表访问权限。
发布配置的 `formHosts` 已收紧为该团队租户 `icnhqa31jmpu.feishu.cn`，`configUrl` 保持空值。

## 环境变量覆盖

环境变量逐项覆盖文件值，优先级高于文件。三态规则：

| 环境变量 | 效果 |
| --- | --- |
| 没设（`undefined`） | 保留文件值 |
| 空串或全空白 | **显式清空**这一项（例如临时关掉表单通道） |
| 其它值 | 覆盖文件值（两端空白会 trim） |

| 环境变量 | 覆盖的配置项 |
| --- | --- |
| `ELECKOI_BUG_REPORT_FORM_URL` | `form.shareUrl` |
| `ELECKOI_BUG_REPORT_FORM_FIELD_BODY` / `_META` / `_CODE` / `_FILE` | 四个字段名 |
| `ELECKOI_BUG_REPORT_MAILBOX` / `_MAILBOX_NAME` / `_SUBSCRIBE_URL` / `_REPOSITORY` | 邮件与仓库通道 |
| `ELECKOI_BUG_REPORT_RELAY_PROVIDER` / `_ENDPOINT` / `_KEY` / `_FROM_NAME` | 代发通道（沿用既有语义） |
| `ELECKOI_BUG_REPORT_CONFIG_URL` | `configUrl`（线上配置的地址，见下一节；空串 = 关掉线上配置） |

只设环境变量、文件里没有 `form` 也可以——`FORM_URL` + `FORM_FIELD_BODY` 给齐就能产出一条表单通道。

## 线上配置（可选）

**不用它也能跑。** 默认 `configUrl` 是空的，客户端一次网络请求都不发。

它解决的问题只有一个：内置 JSON 随包发布，Base 被删或链接填错时，用户手里的版本只能等下次发版。
给一个 `configUrl` 之后，客户端可以在启动时拉一次新的**表单端点**，把用户迁移到新 Base 上。

```json
{
  "form": { "shareUrl": "https://<租户>.feishu.cn/share/base/form/<id>", "fields": { "...": "..." } },
  "formHosts": ["feishu.cn"],
  "configUrl": ""
}
```

- **远程能改什么：** 只有 `form`（分享链接 + 四个字段名）。改不了邮件、代发，也改不了自己的地址——
  下一次拉哪个地址仍由内置文件与环境变量决定。
- **护栏：** 只走 https；响应上限 64 KB；分享链接的主机必须落在 `formHosts`（后缀匹配，默认
  `feishu.cn`）里；形状不对整份丢弃。远程配置**不能扩权**。
- **失败怎么办：** 拉不到、超时（3 秒）、非 2xx、被墙、缓存坏了——全都静默回退到内置配置。
  报告功能不依赖网络。
- **优先级：** 环境变量 > 线上配置（拉到了且合法）> 内置文件。
- **缓存：** `userData/bug-reports/remote-config.json`，带 `fetchedAt`；六小时内不重复拉，
  过期后先用旧值、后台再取。
- **这是信任边界：** 这条链接决定用户的日志发到哪里。别把 `configUrl` 指向不受控的第三方；
  白名单也要跟着收紧（比如只留正式租户的域名）。

## 从零搭一个收件 Base（还没建过的时候看这里）

整套都在飞书网页端完成：**不需要自建应用、不需要 `app_secret`、不需要任何服务器**。
下面的形状来自 2026-10-29 的实测（预填、匿名提交、单条 11,013 字符不截断都验过）。

### 1. 建表：保留四列的用途与类型

新建一个多维表格（Base），第一张表按下表建列；填写页标题按前文映射设置，并同步客户端配置。

| 列名（契约） | 类型 | 放什么 |
| --- | --- | --- |
| `report_body` | 文本（要能存长文本和换行） | 正文：日志尾 + 折叠后的失败列表 + 用户补充说明 |
| `report_meta` | 文本 | 签名 · 版本 · 平台 · 架构 · 生成时间 · 上次会话 |
| `report_code` | 文本 | 失败码列表（空 = 没记到失败行，通常是原生崩溃或强杀） |
| `report_file` | 附件 | 附件位。客户端**不上传文件**，只预填一句「完整 JSON 用导出文件另存」 |

`report_body` 必须是能留住整段的文本列：实测 11,013 字符（含中文与换行）原样入库、读回来长度不变。

当前正式表单按题目标题预填（`?prefill_<题目标题>=<URL 编码值>`）。新建或更换表单时必须实际验证，
不能仅凭列名或 CLI 字段 ID 推断预填一定生效。

### 2. 建表单视图，把四个问题绑到四列

在 Base 里加一个「表单」视图，四个问题分别绑定上面四列。用户看到的中文题目标题按前文映射设置，
并与两端客户端的预填配置保持一致；附件保持可选。

### 3. 分享设置：允许匿名填写

表单的分享设置必须是（界面文案大致是「任何人可填写 / 允许匿名填写 / 不要求登录」，下面是对应的内部键）：

- `access_scope=anyone` —— 拿到链接的人都能填
- `allow_anonymous=true` —— 允许匿名填写
- `require_login=false` —— 不要求登录

三项缺任何一个，用户就会撞到登录页或权限申请，表现得像按钮坏了。这三项是 2026-10-29 从实际表单
读回来的值；界面上的措辞可能随飞书版本变，实际以「未登录能用浏览器打开并提交」为准。

### 4. 复制**填写页**链接（不是分享链接）

从浏览器地址栏复制，必须含 `/share/base/form/`：

```text
https://<租户>.feishu.cn/share/base/form/shrcn…
```

飞书 `+form-share-get` 返回的 `.../share/base/shrcn…` 少了 `form` 这一段，未登录会 302 到
`accounts.feishu.cn`。客户端只追加参数、不做推导也不校验形状（决定 12），复制错就只是「表单打不开」。

### 5. 填进两处配置

- 桌面：`apps/desktop/resources/bug-report.json` 的 `form.shareUrl` 与四个题目标题 `fields`
- Android：`apps/android/app/src/main/res/values/strings.xml` 的 `bug_report_form_url` 与四个题目标题

两处必须一致（`apps/android/tests/android-bug-report-facts.test.js` 有用例钉住）。租户不在
`feishu.cn` 下（飞书国际版、自有域名）时，还要把域名加进 `formHosts`，否则**线上配置**那条路
会被静默拒绝，而内置链接照样能用，排查起来很难看。

### 6. 提交一条测试记录

用真实客户端走一遍，或在浏览器打开带预填参数的链接，确认表里 `report_body`、`report_meta`、
`report_code` 三列都有值。缺一列就是问题没绑对列。

### 7. 可选：让这张表好管

- 加一列「状态」（新建 / 已确认 / 已修复 / 重复 / 无法复现），表格视图按它筛。
- 按 `report_meta` 第一段的「签名：`<失败码>@<版本>:<平台>`」分组，同一台机器反复提交同一错误会聚在一起。
- 导出 CSV / Excel 离线 `group by` 签名后合并同类。

飞书不会替我们做去重、限流，也不发通知；要不要验证码、要不要限制重复提交，得在表单设置里配，
客户端不能假设。

## 换 Base 时怎么刷新

已有 Base、只是要换一个新的：

1. 按上一节 1–4 步在新 Base 里建好四列与表单视图，拿到带 `/share/base/form/` 的填写页链接。
2. 把链接与四个**题目标题**填进 `bug-report.json` 的 `form.shareUrl` / `fields`，同时改安卓
   `strings.xml`。
3. 题目标题优先沿用当前客户端配置——老版本客户端只会按原题目标题预填，换了标题它发出的
   就是空表单。
4. 提交一条测试记录，确认表格里正文、元信息、失败码都在，再发版。
5. 旧 Base 别急着删：老版本客户端仍会往旧链接发，观察一段时间再停用。想不发版就让用户迁移，
   配 `configUrl`（见上一节）。

## 红线：客户端不放服务端凭据

飞书自建应用的 `app_secret`、企业微信 Secret、GitHub token、SMTP 授权码一律**不进**这个文件，
也不进任何环境变量——拆包即泄露，后果是能以你的身份读写整个租户。表单分享链接与自定义机器人
webhook 是另一类凭证：只能往指定表 / 群写，泄漏的后果是脏数据而非数据外泄，即便如此也要能轮换
（重建表单、删机器人），不能当作身份使用。

维护者在本机使用 CLI 管表时，认证留在 CLI 的本机凭据库，与客户端发布配置分开。
报告脱敏覆盖已识别的路径、用户名、邮箱、凭据参数、大陆手机号及明确的电话字段；不能据此保证
任意自由文本里的个人信息都能识别，用户仍应在提交前检查预览。匿名表单的防刷及收到报告的保留期
需要维护者另行管理，客户端草稿的 30 天清理不等于飞书收件表也会自动清理。

## 客户端几乎不发请求

客户端只把预填参数拼到分享链接后面，然后交给系统浏览器（`openExternal`）。没有飞书凭据、
不调 `+form-submit`、**不上传报告**——提交是用户在看过的表单页上按的那一下。

唯一的例外是**配了 `configUrl` 时拉一次投递配置**（上一节）：启动时后台拉、只读 `form`、
失败静默。默认没配，所以默认形态下客户端确实一次请求都不发。

## 去重与限额：客户端挡掉了什么，飞书那边不管什么

**会被淹没吗？** 先看客户端已经挡掉的：

- **没有自动上传。** 客户端从不主动发请求，也没有队列：用户点「提交到飞书」→ 浏览器打开填好的表单 →
  用户自己在飞书页上按提交。没有「后台补发」，关掉对话框就不再动作。
- **一份报告里同码只留一条。** 崩溃循环不会把一份报告写成几百行：`foldBugReportFailures` 按失败码折叠，
  最多 20 条（`BUG_REPORT_MAX_FAILURES`）。
- **草稿按签名去重。** 同一签名（`<失败码>@<版本>:<平台>`）只留最新一份，最多 10 份、30 天过期——
  同一台机器反复失败不会在本地堆一摞。
- **预填里带着签名。** `report_meta` 的第一段就是 `签名：<失败码>@<版本>:<平台>`，`report_code` 另给失败码列表，
  所以**重复提交可以离线合并**（表格按签名分组，或 `lark-cli` 导出后 group by）。

**飞书那边不管什么。** 多维表格是收件箱，不是我们的服务端：它不会按签名去重，也不替我们限流；
表单要不要验证码、要不要限制重复提交，取决于这个 Base 的表单设置，得在飞书后台确认，客户端不能假设。

**所以剩下的风险是：** 同一个用户手动重复提交同一份（落重复行，可离线按签名合并），以及大量用户各自提交
不同错误（那是正常反馈量）。客户端**没有**按来源/时间的节流——它只有用户点下去的那一下。

**要服务端去重/限流时**，那正是代发通道（`relay`）预留的接缝：签名已经在 `report_meta` 里、投递契约
（`delivery.ts` 的 `relay`）也在，将来上了 Worker 就在那一层做去重、限流与分级告警，不用改客户端。
现在默认配置不配 `relay`，「直接发送」按钮就不会出现。

**维护者侧今天就能做的低成本去重：** Base 里加一列「签名」并用它分组/视图过滤；或定期导出后按
`report_meta` 的签名段合并同类。
