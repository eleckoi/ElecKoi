# ADR 0042：Bug 报告的投递（飞书表单收件箱、邮件与复制兜底）

## 状态

已采纳，2026-10-27。契约在 [`packages/shared/src/contracts/bugReport/`](../../packages/shared/src/contracts/bugReport/)，由 `packages/shared/tests/bug-report.test.ts` 守着。桌面端与 Android 端的收集入口、发送入口、收件箱仓库的折叠 workflow 与 zip 导出按同一契约分平台补齐。

2026-10-29 修订：实测确认飞书多维表格表单可匿名填写并接受 URL 预填，**它成为默认收件端点**（决定 12）；客户端不再提供 GitHub 提交入口（决定 4 修订）；第三方代发与自建 Worker 降为可选（决定 9 / 10 修订）；新增决定 11、13、14、15、16。

2026-10-29 实现落地：飞书表单通道（决定 12）、复制先行与打开失败带码（决定 13）、草稿与跨启动提示（决定 14）、崩溃证据默认带上（决定 15）、内置配置与环境变量覆盖（决定 16）已在客户端实现，桌面与 Android 同形；维护者手册见 [报告投递端点配置](../bug-report-endpoint.md)。2026-11-05：决定 14 的「打开后草稿保留」与决定 16 的线上配置（可选、默认关闭）补进实现。

2026-11-06 追加决定 17：「运行错误」对话框里也留一个入口，错误码预填进补充说明。主入口（社区弹窗）不变。

## 背景

用户反馈现在只有一条路：QQ 群（`CommunityDialog` 里的群号）。维护者拿到的是"我这边闪退了"这种句子——没有版本、没有失败码、没有日志尾，来回问三轮才知道是哪一步。

仓库其实已经把诊断信息准备齐了：[ADR 0040](0040-error-contract.md) 让每次失败带契约码与参数化详情，`AppLog` 给每次运行写会话首尾，"有 start 没 end 就是崩溃或强杀"（[错误处理协作声明](../error-handling.md)）。缺的只是把这份信息送到维护者手里的一段。

先要回答"送到哪里"：

1. **自建服务器**（自托管 Sentry、GlitchTip、自写端点）。个人维护的开源桌面应用，没有运维预算、没有 SLA，也不该多一个需要备份和防滥用的东西。排除。
2. **托管错误服务**（Sentry / Bugsnag 的 SaaS 免费档）。能按 fingerprint 聚合并计数，额度也够，但数据出境要单独征得同意，要推翻 [ADR 0040](0040-error-contract.md) 决定 1 的"不引入运行时错误服务"，而且 Windows 与 Android 要各上一套 SDK。留作量变大后的备选。
3. **邮件**。不占 issue 列表，不需要用户的 GitHub 账号，也不需要接收端点——用户本来就有邮箱。
4. **GitHub issue**。天然可追踪、可引用、可附附件，但两个硬伤：目标用户大多没有 GitHub 账号；每条报告开一个 issue 会淹没列表——issue 没有 fingerprint 聚合，那是另一类服务的核心功能。

3 和 4 覆盖的是不同的人：邮件覆盖"随手反馈"的大多数，issue 覆盖"愿意细致描述、也愿意被追踪"的少数。所以不是二选一。

## 决定

1. **两条通道并存，由用户在发送时选：邮件或收件箱仓库的 issue。** 第三条兜底是导出 zip，用户自己附在群里或邮件里。三条共用同一份报告。
   （2026-10-29 修订）通道顺序改由决定 11 排定：飞书表单是默认端点，邮件与复制 / 导出是兜底；issue 不再由客户端提交。
2. **报告是用户发起的导出，不是后台常驻上报。** 不启动 `crashReporter`（它的 `submitURL` 必填，等于必须有接收端），不引入 Sentry / Bugsnag SDK。[ADR 0040](0040-error-contract.md) 决定 1 的"不引入运行时错误服务"继续有效——本记录不推翻它，只是给"上报"补一条用户可触发的出口：出口仍然是 `AppLog`，加上用户主动的导出。**代发通道（决定 9 / 10）也不是后台采集**：它只在用户点了按钮之后发那一次，不排队、不重试、不上报没点过的内容。
3. **一份报告，两个格式化器。** `BugReport` 形状、校验、失败折叠与脱敏在 `contracts/bugReport/`；邮件正文与 issue 正文各有格式化器，主题与去重键共用 `bugReportSubject` / `bugReportSignature`。`schemaVersion` 显式，字段只增不改。
4. **issue 通道进收件箱仓库，不进化码主仓库。** 报告先落到一个独立仓库（例如 `KuramiWan/eleckoi-reports`），workflow 按签名折叠：同一签名追加成评论并关闭新 issue，不同签名才留成一条聚合 issue。主仓库的 issue 列表一条都不涨，值得修的再由维护者引用过去。**这是用户发起提交，不是客户端自动建 issue**——后者需要一个 token 或端点，见否决表。
   （2026-10-29 修订）**issue 的创建整体移到维护者侧**：客户端不再渲染「在 GitHub 提交」按钮。目标用户没有 GitHub 账号，那条路走不通。折叠 workflow 仍然有效，只是输入从"用户点开的链接"变成"维护者或 Worker 建的 issue"。
5. **仓库里不硬编码收件邮箱，也不硬编码收件仓库。** 公开仓库里的地址会被爬虫抓走。两者都由发布配置注入，契约只提供 `buildBugReportMailto(report, mailbox, letter)` 与 `buildBugReportIssueUrl(report, { repository })`。
   邮件目的地**可以是一个邮件列表**：配置里另给显示名（`mailboxName`）与订阅地址（`subscribeUrl`），正文页脚会写明"已投递到哪、想跟进怎么订阅"。邮件通道没有回执，不订阅就跟丢了；这也是列表相对个人邮箱的真正好处——换维护者变成列表成员管理，不用改发布。
6. **脱敏是纯函数，日志尾默认不带。** `redactReportText` 与 `redactBugReport` 覆盖家目录（Windows / macOS / Linux）、Android 沙箱路径、用户名、邮箱与常见凭据参数；日志尾默认关闭，用户勾选才带。两条通道共用同一份脱敏结果。
7. **长度按编码后计算，超限降级成摘要。** 正文装不进 `mailto:` 或 issue URL 时只带签名与摘要，全文交给剪贴板；宁可多一步粘贴，也不要发出半份日志。
   （2026-10-29 修订）飞书表单的预算是编码后 URL ≤ 32,000 字符（见决定 12）；`mailto:` 仍是 1,800。
8. **Windows 与 Android 共用一份契约。** 两边各写收集与入口，字段、主题、脱敏规则一致。
   Android 没有 Electron 主进程，收集只能落在 Java：它已经有一套受限运行诊断（`RuntimeDiagnostics`，key 白名单 + 凭据脱敏），补一对会话标记后把「环境 / 上次会话 / 最近事件 / 投递配置」作为**原始事实**交给渲染层，报告由共享的纯函数拼（`packages/shared/src/foundation/bugReport.ts`）。所以拼装、脱敏、折叠、正文格式仍然只有一份实现；Java 只负责它擅长的存储与文件 IO。2026-11-05 修订：**两个变体都提供入口**——标准版也启用运行诊断（[ADR 0031](0031-android-local-node-host.md) 同日修订），报告原料与兼容版一致；原先「第一版只在 compat 变体提供入口、标准版不给按钮」作废。
9. **代发通道可选，默认关闭。**（2026-10-29 修订：被决定 12 取代。契约保留，不再默认使用——表单端点不需要密钥、不需要服务器，额度与境外可达性的问题一起消失。） `mailto:` 在没配默认邮件客户端的 Windows 机器上点了没有反应，这是邮件通道最实际的坎。所以允许配一个托管代发服务（当前支持 Web3Forms 与 Formspree），由主进程 `POST` 出去。三条约束写死在契约里：**端点必须是 https**、**只收客户端公开标识**（Web3Forms 的 access key 与 Formspree 的表单地址本来就是给前端用的；任何"只在服务端用"的密钥都不进这个形状）、**没配就不显示按钮**。代价明说：报告会经第三方中转、公开标识可被提取并耗掉免费额度（Web3Forms 250 封/月、Formspree 50 封/月）、服务都在境外、连不上时按钮失败并回落到复制与导出。

10. **自有 Worker 中转（双写），默认不部署。**（2026-10-29 修订：降为可选，见决定 16 末段。） `eleckoi-relay` 是一个 Cloudflare Worker：客户端只认这一个端点，后面接什么由服务端决定。第一版两个落点、两种节奏：
    - **收件箱仓库 issue，实时。** 每个签名一条聚合 issue，重复报告追加成评论。Worker 用存在自己 secret 里的 token 建 issue，所以**报告人不需要 GitHub 账号**——这也是当初否掉"自动建 issue"的两条理由同时失效的地方。
    - **邮件列表，每天一封摘要。** 今天的新签名、各出现几次、涉及哪些版本。**不逐条抄送列表**：双写不加聚合，等于把"淹没"从 issue 搬到邮箱。
    清洗与聚合分工（决定 10 的边界，跨语言实现也要守）：
    - **客户端**负责真正的隐私：脱敏、日志尾默认关、发送前可预览可删改。
    - **Worker 入口**负责结构化防线，**不负责判断内容是否私密**：`schemaVersion` 白名单、请求体 ≤ 256KB、`details` 只留已知键、日志尾只留像日志的行并按行数与字节双限截断、二次宽脱敏（独立实现，不 import 客户端代码——客户端是公开可改的）。
    - **Worker 聚合**负责去重与计数：签名由 Worker 从报告重新派生（不信客户端算的那份），正文 hash 去重（同一份点两次只算一次），`signatures` 表存签名 → issue 编号与计数。**不用 GitHub 搜索 API 查重**（30 次/分钟，会先撞限流）。
    - **issue 正文**由 Worker 维护成固定结构：签名、首次出现、累计次数、版本分布；评论只追加。这样一条 issue 从第 1 条报告到第 200 条都还读得懂。
    - **限流**：每 IP 每天 5 条、每签名每天 20 条（防一台机器循环崩溃刷爆）。客户端里的任何"密钥"都可被提取，**防线只在服务端**，它不是身份。
    - **保留期**：`reports` 明细 30 天（Cron 清理），`signatures` 长期；issue 与邮件本身已经是留档。

11. **投递是一条链，不是一个按钮组。** 通道按"用户还要做几步"排：**零输入的端点**（飞书表单：点开、提交）→ **需要一个本地客户端**（`mailto:`）→ **完全手动**（复制、导出文件）。
    - 复制是地板：任何时刻都有它，且不依赖任何外部程序。
    - **没配端点时不渲染会失败的发送按钮。** 反过来也成立：配了但一定连不上，按没配处理——连不上一次之后，本次会话内把它降为次级，不让用户在同一个死端点上反复等。
    - GitHub issue 不再是用户侧通道（决定 4 修订）。它只作为维护者侧的归档形态：Worker 建（决定 10），或维护者用本地脚本把表格里的报告推过去。

12. **飞书多维表格表单是默认收件端点。** 形态：维护者建一个 Base（一张表 + 一个表单视图），分享设成"任何人可填写 + 允许匿名 + 不要求登录"；客户端内置**表单分享链接**，把已脱敏的正文放进 URL 预填参数，用户在浏览器里点一次提交。
    - 预填格式 `?prefill_<题目>=<URL 编码值>`，按题目的**字段名或字段 id** 匹配。字段名是契约：`report_body`、`report_meta`、`report_code`、`report_file`（附件，用户自己把导出文件拖进去）。**改题目名等于破坏预填**，所以题目名一旦发布就不动，展示文案另设。
    - **内置的是完整分享链接，不是 base token。** 租户域是随机串，`+form-share-get` 返回的 `.../share/base/shrc…` 未登录会 302 到登录页；只有 `.../share/base/form/shrc…` 能匿名打开。这个路径形状没有文档保证，所以由维护者从界面复制，客户端只追加参数，不做推导。
    - **预算按编码后 URL 算，上限 32,000 字符。** 实测（2026-10-29）：60,000 字符的链接预填完整生效，100,000 字符连接被重置。超限时先截断日志尾并注明，再不行只带摘要，最后提示用户改用导出文件走附件字段。
    - 为什么是它：不需要收件服务器、不需要用户的任何账号、不需要加群，而提交动作仍然是用户点的（决定 2 不变）。代价是报告存在第三方（飞书）里，且链接泄漏后可以被刷——脏数据只能人工删。
    - **不做表单 API 直连。** 客户端没有飞书凭据，也不该有；`+form-submit` 这类接口属于维护者工具链。
    - 实测（2026-10-29）：匿名提交后记录入库、提交者为访客；11,013 字符的正文原样入库，无截断。

13. **先落剪贴板，再打开外部程序。** 每一次投递动作的顺序固定：`formatBugReportBody` → 写剪贴板 → `openExternal`。
    - 打开失败折成 `eleckoi/shell/open-failed`，`details` 带 `{ what: 'mail' | 'form' }`；用户可见文案由渲染层给（"没能打开系统里的对应程序"），并写明下一步"把全文粘到任意地方发给作者"。**剪贴板那一步真的成功时，界面才说"全文已复制"**：剪贴板也可能被系统占用，宣称一件没发生的事比少说一句更糟。
    - **打开失败不自动改开别的通道。** 用户点的是"发邮件"，突然弹出浏览器是惊吓，不是兜底。
    - 理由：外部程序的"成功返回"只代表系统接住了调用。Linux 上 `xdg-open` 找不到处理程序时仍会 resolve，所以"已打开"不是承诺，剪贴板才是。

14. **失败不丢，但也不偷偷重发。** 发送失败或用户中途关闭时，已脱敏的报告写进 `userData/bug-reports/pending/<key>.json`；发送成功才删，30 天后清理。
    - 下次启动最多提示一次"上次有 N 份没发出去"，用户点了才重发。不排队、不自动上传（决定 2）。
    - 自动重试只发生在用户点下去的那一次会话里，且只对 `5xx` / `429`；网络层失败（连不上、DNS、TLS）直接失败并降级——连不上再试还是连不上。
    - **表单通道没有"提交成功"这个信号。** 打开浏览器只说明系统接住了调用（决定 13），所以打开后草稿**保留**，由用户确认提交后自己点「丢弃」——不能因为"打开成功"就替用户宣布送出去了。
    - 同一签名的草稿只留最新一份：崩溃循环不该把清理额度吃满，更不该把几天前的旧草稿挤掉。

15. **崩溃证据默认带上，崩溃现场保鲜。** 上次会话"有 start 没 end"时，日志尾默认勾上，并在对话框里写明"这次是异常结束，建议保留日志尾"。
    - 会话判定跨启动可见：取**最近一次没有 `ended` 的会话**并写出它的开始时间，不能只看最近两次开始——否则崩溃隔两次启动就变成"正常结束"，证据自愈掉了。
    - 理由：报告的价值在证据。默认不带日志尾，等于到手的报告大多只能看出"崩过"。

16. **配置可缺失，凭据不进客户端。** 投递配置来自构建时打进包的内置文件，环境变量只做覆盖；文件缺失或损坏按"未配置"处理，永不抛。
    - **红线**：只在服务端用的凭据一律不进客户端——飞书自建应用的 `app_secret`、企业微信自建应用的 Secret、GitHub token、SMTP 授权码。拆包即泄露，而且泄露的后果是别人能以你的身份读写整个租户。
    - 飞书**表单链接**与自定义机器人 **webhook URL** 是另一类：只能往指定表 / 群写，泄漏的后果是脏数据或刷屏，不是数据外泄。即便如此，它们也必须能轮换（重建表单、删机器人），且不能当作身份使用。
    - 决定 10 的 Worker 因此降为**可选**：它换来的是折叠、计数与每日摘要，量小时表单 + 维护者本地 ingest 已经够。部署与否不改变客户端形态。
    - **2026-11-05 修订：线上配置（`configUrl`）是可选通道，默认关闭。** 内置文件随包发布，Base 被删或链接填错时用户手里的版本只能等下次发版，所以留一条「拉一次表单端点」的路。约束与上面同源：只走 https、响应上限 64 KB、只读 `form`（分享链接 + 四个题目名）、分享链接主机必须落在随包发布的白名单 `formHosts`（默认 `feishu.cn`）里、远程配置改不了自己下一次拉取的地址（`configUrl` 只从内置文件与环境变量来）、任何失败静默回退到内置配置。**优先级：环境变量 > 线上配置 > 内置文件。** 这条链接决定用户的日志发到哪里，是信任边界；因此远程载荷不能扩权，白名单随版本收紧。Android 暂时没有这条通道（配置编译在 `strings.xml` 里），是已知差异。

17. **出错的那一刻也能报告：错误对话框里给一个入口。**（2026-11-06 追加）「运行错误」对话框（`AppErrorDialog`）在报告服务可用时多一个「报告问题」按钮；社区弹窗那个入口保留，两者打开的是同一个对话框、同一份报告。
    - **只在有报告服务时渲染。** 与决定 11 同一条规矩：没有桥、没配端点就不画这个按钮——绝不渲染一个点下去必然失败的控件。报告对话框挂在三个宿主窗口里（主窗口 / 独立聊天窗口 / 安卓），谁挂了谁的错误对话框才有这个按钮；没挂的窗口不传回调，按钮不出现。
    - **点一次做两件事**：关掉这条错误提示，打开报告对话框（不叠两个模态）；并把刚看到的**错误码**预填进「补充说明」。理由：渲染层失败只以 `eleckoi-renderer-failure` 诊断行进日志尾，**不进**报告里折叠出的失败列表（那份列表来自主进程 `phase: failure` 记录），不预填的话用户从错误点进来可能看到「没有记录到失败行」，代码只剩他自己记得。预填的是可删可改的补充说明，不改变报告的字段契约。
    - **决定 2 不变**：这是入口不是通道，报告仍然由用户点出去，不自动上传、不排队。

## 否决的方案

| 方案 | 为什么不用 |
| --- | --- |
| 客户端自动建 issue（内嵌 GitHub token） | 公开仓库里发布即泄露，拆包就能拿到。 |
| 客户端提供「在 GitHub 提交」入口 | 目标用户没有 GitHub 账号，点进去先撞登录墙（决定 4 修订）。issue 只作为维护者侧的归档形态。 |
| 客户端内嵌飞书自建应用的密钥 | 与 token 同理：拆包即泄露，且泄露的后果不是脏数据，是能读写整个租户。表单链接只能往一张表写，是另一类凭证（决定 16）。 |
| ~~端点代建 issue（Worker / 函数）~~ | **已由决定 10 采纳并限定**：单 Worker、不落原文、失败回落。原否决理由（要部署、要防滥用、要管密钥）仍然成立。2026-10-29 再降为可选（决定 16）：报告量小时，表单加人工就够。 |
| 报告直接进主仓库 issue | 会淹没主仓库；要修的问题和"又来一条同类报告"混在一起。 |
| Sentry / Bugsnag 的 SaaS 免费档 | 数据出境要单独征得同意，且要推翻 ADR 0040 决定 1。 |
| 客户端内嵌 SMTP 授权码 | 同 token：发布即泄露。 |
| Windows 自带 WER / App Center | WER 要注册开发者服务；App Center 已停止服务。 |

## 后果

- **没有自动到达的报告。** 收到多少取决于用户是否点"发送"。这是刻意的取舍：不需要服务器，也就意味着没有后台推送。
- **默认形态不需要任何服务器。** 收件是飞书 Base，读是浏览器或 `lark-cli`；Worker 只在报告量上来之后才有净收益。
- **填写与阅读之间多一步「提交」。** 用户点开链接时报告已经填好，但仍要按一次提交——这是这条链路唯一的人工成本。
- **表单链接泄漏的后果是脏数据，不是数据外泄。** 删行即可；自定义机器人 URL 泄漏的后果是刷屏。两者都不该被当成身份（决定 16）。
- **Worker 中转的净收益随报告量增长。** 每天十条以下，人工翻表也够；上百条时，服务端的折叠与每日摘要才是唯一撑得住的形态。
- 要多养三样东西：一个飞书 Base（表单 + 表）、一个收件邮箱、一个收件箱仓库（Worker 上线后才用得上）。都不影响主仓库。
- 邮箱侧靠主题前缀 `[ElecKoi]` 建规则；issue 侧靠正文里那行隐藏的签名注释块折叠。
- 若将来量变大要自动化，`BugReport` 已是稳定形状，接端点不用改客户端。
- 客户端已有：飞书表单通道（决定 12）、复制先行与打开失败带码（决定 13）、草稿与跨启动提示（决定 14）、崩溃证据默认带上（决定 15）、内置配置与环境变量覆盖（决定 16）、错误对话框里的入口与错误码预填（决定 17）。
- 仍然不做：客户端自动建 issue、客户端内嵌任何服务端凭据、后台自动上传；`eleckoi-relay` Worker 与第三方代发仍是可选（决定 10 / 16），报告量证明需要之前不部署。
