# Agent 的 Token 消耗与回复速度

[返回公开课题目录](README.md) | [English](token-cost-and-speed.en.md)

**状态：公开课题，尚未解决。**

这是目前大家最关心的问题。

## 为什么 Agent 更慢、消耗更多

传统 Chatbot 通常一次请求就产生一段回复。Agent 在同一回合中可能先理解任务，再搜索设定、读取变量、调用工具、接收工具结果，最后继续请求模型生成正文。因此，一次用户对话可能对应多次模型请求；每增加一次请求，都可能再次携带当前上下文并产生新的输入与输出 Token。

回复速度也不只由模型生成速度决定，还包括设定检索、工具执行、网络等待、多轮模型续接以及最终正文生成。只看最后一段文字的生成速度，无法反映 Agent 的完整等待时间。

## 当前实现

- 角色聊天目前仍把已有的 `user/assistant` 对话数组作为长期历史。每一次模型请求，包括同一 Agent 回合中的多次续接，都会重新携带这段历史。
- 旧回合的推理、工具调用和工具结果不会作为长期对话再次发送给模型。
- 当前回合中的工具调用和工具结果会保留到该回合结束，确保模型能够根据刚刚取得的结果继续工作。
- 工具调用时间线可以作为界面和执行记录保存，但“保存供用户查看”不等于“下一回合再次发送给模型”。
- 模型厂商的上下文缓存可以在命中时缓解部分重复计算或计费，但缓存可能失效，也不解决上下文长度持续增长和注意力被大量旧对话分散的问题，因此只能视为当前缓解手段，不能代替聊天记录设计。
- 项目对角色聊天记录利用方式的探索还很少，目前基本是把已有的用户与助手正文全部装入上下文，尚未形成成熟的压缩、摘要、分层或检索策略。

## 尚未解决的问题

- 哪些近期消息必须保留原文，哪些较早内容可以压缩？
- 怎样压缩剧情而不丢失人物关系、承诺、因果和叙事语气？
- 怎样避免每次模型续接都重复携带不再需要的提示词和工具上下文？
- 能否由专门的历史管理子 Agent 处理 `user/assistant` 对话，按当前剧情为主 Agent 准备上下文？怎样防止它遗漏伏笔、人物关系和关键原话，同时避免新增请求反而消耗更多 Token 和时间？
- 怎样同时衡量请求次数、输入与输出 Token、缓存命中、工具耗时、首字延迟和整轮完成时间？
- 怎样降低成本和等待时间，又不把 Agent 退化成只能一次性回复的普通 Chatbot？

## 当前计划

项目现阶段优先完成基础链路建设，尚未对聊天记录压缩投入系统性的深入研究。随着 Agent 架构继续发展，聊天记录也可能从被动装入的数组变成由专门能力主动整理的上下文，但这仍只是需要验证的研究问题。后续将先建立可重复的真实对话测量方法，再比较直接全量装入、历史裁剪、摘要、检索和子 Agent 管理等方向。这里先公开抛出问题，不预设最终答案。
